1. Cursor basics

What Cursor is

Cursor is a desktop AI code editor whose main product surface is Agent. You also run the same agent loop as Cloud Agents on the web and mobile, so work can continue without your laptop staying open.

Think of three layers:

  • Editor — open a folder, edit files, use Tab and inline edit.
  • Agent — a goal-driven loop with tools: search, edit, terminal, browser, and more.
  • Cloud Agents — the same loop on an isolated VM, started from cursor.com/agents, desktop, Slack, GitHub, Linear, or mobile.

Composer 2.5 is a model you pick in the model picker. Agent is the product surface. Do not confuse Composer 2.5 with the old Composer UI.

Learn by doing

Install or open Cursor, then open any repo folder. You should see a normal editor plus an Agent input. That Agent panel is the surface you will use for almost everything below.

Official video: Introducing Cursor 3

Cursor’s launch video for the agent-first workspace, local/cloud handoff, and running many agents.

Open a folder and start Agent

Agent, project rules, skills, and project MCP config are scoped to the folder you opened. Open the repo first, then start Agent.

  1. File → Open Folder (or open the repo from the welcome screen).
  2. Press Cmd+I on Mac or Ctrl+I on Windows/Linux.
  3. Type a specific task and press Return.
Better first prompt 
Add a settings page that matches src/pages/Profile.tsx.
Include display name, email notification toggle, and theme dropdown.
Reuse existing form components. Do not introduce a new UI library.

Watch edits in the diff view. Use Stop to interrupt. Hover a previous message and restore a checkpoint if the agent went the wrong direction. Checkpoints are local snapshots, not a replacement for Git.

How Agent mode works

Agent mode searches the codebase, edits files, runs terminal commands, and iterates until the task is done or you stop it. Under the hood it is an agent harness:

  1. Instructions — system prompt plus your rules.
  2. Tools — read/search files, edit, shell, browser, web, image generation, clarifying questions, and more. There is no hard cap on tool calls.
  3. Model — the model you pick (or Auto / Cursor Router).

An agent is “tools in a loop.” You give a destination; it chooses the next tool based on the last result. Your job becomes direction and review, not typing every step.

Queue follow-ups with Enter while it works. Send immediately with Cmd/Ctrl+Enter. Start a new chat when the task changes so context stays clean.

Learn by doing

Ask Agent to add a failing test for one existing function, run the test suite, then make only that test pass. Watch which files it opens and which commands it runs.

Agent, Ask, Plan, and Debug

Cycle modes with Shift+Tab or the mode picker. Each mode starts a fresh context window.

  • Agent — default. Edits files and runs commands. Use for building, refactors, fixes, and verification.
  • Ask — read-only. Use when you want explanation without changes.
  • Plan — researches the repo, asks clarifying questions, writes a reviewable plan. Click Build only after you approve it. Plans save locally; use Save to workspace to keep them in the repo.
  • Debug — for tricky bugs that need runtime evidence. It can edit while gathering that evidence.

Project, user, and team rules apply in all four modes. They do not apply to Tab or inline edit.

When to use Plan

Multi-file features, several valid approaches, unclear requirements, or architecture choices. For a one-function rename, stay in Agent.

Learn by doing

Switch to Plan and ask for a notification-preferences feature. Answer the clarifying questions, edit one milestone in the plan, then click Build. If the result is wrong, revert to the plan and tighten it instead of piling on chat fixes.

Tab autocomplete

Tab is next-edit prediction as you type, not the Agent panel. Suggestions appear as ghost text from recent edits, nearby code, and linter errors.

  • Accept all: Tab
  • Reject: Esc or keep typing
  • Accept word by word: Cmd/Ctrl+→
  • After an accept, Tab again can jump to the next edit location, including another file.

Turn Tab off from the status bar indicator (snooze, disable globally, or disable by file type) or Cursor Settings → Tab.

Learn by doing

Rename a function in one file and keep typing call sites. Notice when Tab jumps to the next usage instead of only finishing the current line.

Inline edit with Cmd/Ctrl+K

Inline edit is a surgical change in the current selection. It does not open Agent and does not use user rules.

  1. Select the code.
  2. Press Cmd+K / Ctrl+K.
  3. Describe the change, then Return.
  4. Follow up in the same inline session if needed.

Question mode: Opt/Alt+Return inside inline edit. To escalate to Agent with the selection as context, use Cmd/Ctrl+L.

Good inline-edit prompts 
Convert this function to async/await.
Add null checks without changing the return type.
Rewrite this as a switch on status.
@ mentions and context

Type @ in the Agent input to attach exact context. Official mention types include:

  • Files and folders, e.g. @auth.ts or @src/components/
  • Terminal output via @Terminals
  • Git: uncommitted diff or diff vs main
  • Browser context via @Browser
  • Past chats

If you know the file, mention it. If you do not, skip @ — Agent can search. The context ring next to the input shows how full the window is (system prompt, tools, rules, skills, MCP, conversation, summaries).

You can also paste images or screenshots. Voice input is available from the mic icon on the input.

Learn by doing

Start a prompt with @ and attach one folder plus the git working-tree diff. Ask Agent to explain only what changed and whether tests cover it. Do not ask it to edit yet (or switch to Ask).

Rules and AGENTS.md

Rules are persistent instructions injected into Agent context. Precedence is Team → Project → User.

  • Project rules — .cursor/rules/*.mdc, version-controlled. Apply always, by glob, intelligently from a description, or only when @-mentioned. Plain .md files in that folder are ignored.
  • User rules — Customize → Rules. Global style preferences. Agent chat only.
  • Team rules — dashboard, Teams/Enterprise. Can be enforced so members cannot disable them.
  • AGENTS.md — plain markdown in the repo root or nested folders. Nested files combine; closer folders win. Use this when you do not need .mdc frontmatter.
Example project rule 
---
description: API validation conventions
alwaysApply: false
---
- Validate inputs with zod at the route boundary.
- Never throw raw strings; return { code, message }.
- Follow src/services/paymentService.ts as the template.

Create rules with /create-rule in Agent or from Customize → Rules. Keep rules short and concrete. Do not dump an entire style guide; use a linter for that.

Skills (SKILL.md)

Skills are portable workflow packages. Unlike always-on rules, a skill is included when Agent decides it is relevant, or when you type / and pick it.

Discovered from .cursor/skills/, .agents/skills/, matching user-level folders, and compatibility paths such as .claude/skills/. Each skill is a folder with SKILL.md:

---
name: deploy-app
description: Deploy to staging or production. Use when the user mentions deploy or release.
---
# Deploy App
Run scripts/deploy.sh <staging|production>
Validate first with python scripts/validate.py

Optional scripts/, references/, and assets/ folders load on demand. Built-in skills include /create-rule, /create-skill, /review, and others. View them under Customize → Skills.

Learn by doing

Type / in Agent and open /create-skill. Create a tiny skill that runs your repo’s lint command. Then invoke it by name on a dirty file.

Models picker and Composer 2.5

Pick a model from the dropdown at the Agent input, or cycle with Cmd/Ctrl+/. Mode (Agent/Ask/Plan/Debug) and model are independent.

Composer 2.5 is Cursor’s own agentic coding model, not the retired Composer UI. It sits in the Cursor Models usage pool with Cursor Grok 4.5. Auto / Cursor Router can choose a model for you; Teams often default to Auto.

  • Faster / cheaper models — routine edits and tight loops.
  • Stronger frontier models — hard reasoning, messy multi-file design.
  • You can switch mid-conversation; the new model applies going forward.

Set a default in Cursor Settings → Models. Cloud Agents use a curated subset and let you choose context window size on supported models.

Privacy Mode for teams

With Privacy Mode on, Cursor does not train on your code. Teams typically have Privacy Mode on by default, and admins can enforce it.

Legacy “No Storage” Privacy Mode blocks cloud storage. That disables:

  • Cloud Agents, which must store code and environment data while they run
  • Shared Transcripts, which need stored conversation history

Use standard Privacy Mode, not No Storage, if you need Cloud Agents. Cloud Agents still keep run transcripts and environment snapshots long enough to review and resume. Secrets belong in the Cloud Agents dashboard, not in git.

2. Cloud Agents

Isolated cloud VMs, not your laptop

Cloud Agents were formerly called Background Agents. Each run gets an isolated VM with a full dev environment: clone, dependencies, secrets, startup commands, and network. Your laptop does not have to stay online.

Because the agent has its own computer, it can build, test, drive a browser/desktop, record artifacts, and open a PR. Local Agent competes with you for your machine. Cloud Agents scale out in parallel.

  • Local — edits on your laptop, you watch diffs live, laptop must be available.
  • Cloud — VM, branch + optional PR, artifacts, shareable run URL, many agents at once.

Environment setup is what makes cloud agents useful. Without tests and tools, they cannot close the loop. Configure setup via agent-led setup, a snapshot, or .cursor/environment.json.

Start and review a Cloud Agent

A team admin must connect source control before anyone can start cloud agents on a repo. Then start from anywhere you work:

  • cursor.com/agents on any device
  • Desktop Agent input → dropdown → Cloud
  • Cursor iOS app; Android uses the agents site as a PWA
  • Slack or Linear: @cursor
  • GitHub PR/issue or Bitbucket PR comment: @cursor
  • API

On the run page, review the conversation, diffs, artifacts (screenshots, videos, logs), optional remote desktop, and the PR if the agent pushed. Plan mode can hand a local plan to a cloud agent for implementation.

Good cloud handoff

Plan locally until the approach is clear, then send that plan to Cloud so you can switch tasks. Come back to artifacts + PR instead of sitting on the laptop diff.

Share runs vs Shared Transcripts

Send the Cloud Agent run URL. A viewer needs all three:

  1. Same Cursor team
  2. Their own SCM connected at Integrations
  3. Access to the repository

Team membership alone is not enough. Default view is read-only. Team follow-ups must be enabled by an admin before teammates can continue the run.

Shared Transcripts are different: they share a local IDE chat at cursor.com/s/…, Teams/Enterprise only, and they are unavailable under No Storage Privacy Mode. Do not use a transcript link when you mean a cloud run.

Learn by doing

Open this Cloud Agent run on cursor.com/agents, copy its URL, and confirm a teammate with repo access can open the conversation and diffs.

3. MCP (Model Context Protocol)

What MCP is and how to add it locally

MCP connects Agent to external tools and data — Linear, Notion, databases, APIs — so the agent can act instead of relying on pasted context.

Add servers locally from Customize → MCPs (including marketplace one-click install), or with JSON:

  • .cursor/mcp.json — project, shared via git
  • ~/.cursor/mcp.json — user, every local project
Remote HTTP example 
{
  "mcpServers": {
    "linear": {
      "url": "https://mcp.linear.app/mcp",
      "headers": {
        "Authorization": "Bearer ${env:LINEAR_API_KEY}"
      }
    }
  }
}

Agent uses listed tools automatically when relevant, including in Plan mode. Approval follows the same run-mode rules as terminal commands. Toggle servers in Customize without deleting them. Debug via Output → MCP Logs.

Learn by doing

Install one trusted marketplace MCP you already use (for example Linear). Ask Agent, by name, to list your recent issues. Confirm the tool call arguments before approving.

Team MCP, Cloud MCP, and security

Three distribution paths stay separate:

  • Dashboard → Integrations & MCP feeds Cloud Agents. Linking to the team marketplace does not auto-install for every IDE user.
  • Git mcp.json applies to people who clone the repo locally.
  • Marketplace / Customize install is a personal or team-plugin action.

On Cloud Agents, HTTP is preferred and stdio also works. SSE and mcp-remote are not supported. OAuth is per-user, including for team-shared servers. Manage cloud MCP from the MCP dropdown on cursor.com/agents.

Security:

  • Install only trusted publishers; review what the server can access.
  • Least privilege API keys.
  • Never hardcode secrets in git-tracked mcp.json. Use ${env:NAME}, dashboard secrets, or OAuth.
